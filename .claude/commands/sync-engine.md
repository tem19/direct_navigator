Реализуй движок синхронизации в `src/sync/`. Режим запуска: `$1`
(если пусто — `full` = pull затем push).

Это сердце приложения-аналога Коммандера: пользователь работает офлайн, а движок
приводит локальную БД и Яндекс Директ к согласованному состоянию.

## Логика

### Pull (сервер → локально)
- Для инкрементального обновления используй сервис **`changes`**:
  `changes/checkDict` (когда менялись справочники) и `changes/check`
  (какие объекты изменились с момента `Timestamp` последней синхры). Так не
  выкачиваешь всё каждый раз и экономишь баллы.
- Первичная загрузка (нет timestamp) — полный `get` по всем сущностям с
  авто-пагинацией.
- Пришедшие серверные данные:
  - если локальной строки нет → вставить как `synced`;
  - если локальная `synced` → обновить, сохранить свежий `server_hash`;
  - если локальная `modified` и сервер тоже изменился → пометить `conflict`
    (см. ниже), НЕ затирать правки пользователя молча.

### Push (локально → сервер)
- Собери строки в статусах `new / modified / deleted`.
- Порядок важен из-за зависимостей: сначала родители (кампании), затем группы,
  объявления, ключевые слова. Для `new` дочерних используй `direct_id`, который
  вернулся при добавлении родителя.
- Батчинг: Директ ограничивает число объектов в одном запросе — режь на пачки.
- Разбирай **поэлементный** результат: успех → проставить `direct_id`, `synced`,
  обновить `server_hash`; ошибка → оставить строку изменённой, записать причину
  в лог операции, не роняя весь батч.

### Конфликты
- Тип `Conflict` = локальная версия + серверная версия + список расхождений по
  полям. Складывай в очередь конфликтов; UI (см. `/grid-ui`) даст выбрать
  «оставить локальное / принять серверное / по полям».

### Баллы (units) и лимиты
- Перед push оцени стоимость в баллах; если остаток (из заголовка `Units`
  клиента API) недостаточен — останови и верни понятную ошибку, а не сыпь
  запросами. На `error_code 56` — бэкофф и пауза.

## Что сделать

1. `SyncEngine` с методами `pull()`, `push()`, `full()` и стримом прогресса
   (сколько сущностей, сколько баллов потрачено, ошибки) для UI.
2. Хранение `last_sync_timestamp` per-сущность/аккаунт.
3. Очередь и репозиторий конфликтов + API их разрешения.
4. Журнал операций синхронизации (что, когда, результат) для отладки.
5. Тесты (Vitest) на замоканных API+БД: инкрементальный pull применяет changes;
   push проставляет `direct_id` детям; конфликт детектится; частичная ошибка не
   валит весь батч.

## Критерии готовности

- Повторный pull без изменений на сервере не делает лишних `get` (идёт через
  `changes`).
- Push новой кампании с группой и объявлением проходит в правильном порядке.
- Конфликт помечается, а не теряется.
