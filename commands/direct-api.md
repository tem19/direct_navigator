Реализуй или расширь клиент **Yandex Direct API v5** в `src/direct-api/`.
Цель этого запуска: сервис(ы) `$1` (если пусто — базовый транспорт + `campaigns`).

## Факты об API, которые надо соблюдать

- Формат — **JSON** (не SOAP). Базовый URL берётся из env:
  - боевой: `https://api.direct.yandex.com/json/v5/`
  - песочница: `https://api-sandbox.direct.yandex.com/json/v5/` (дефолт для dev).
- Один сервис = один URL-сегмент: `.../json/v5/campaigns`, `/adgroups`, `/ads`,
  `/keywords`, `/keywordbids`, `/bids`, `/changes`, `/dictionaries`, `/reports`,
  `/adextensions`, `/sitelinks`, `/vcards`, `/audiencetargets`.
- Авторизация: заголовок `Authorization: Bearer <OAuth-токен>`. Токен НЕ хранится
  в `.env`/файлах в открытом виде — клиент получает его из main-процесса, где он
  расшифровывается через `safeStorage` (macOS Keychain). Сырой токен не логируем.
- Обязательные/частые заголовки: `Accept-Language` (`ru`/`en`),
  `Client-Login` (для агентских аккаунтов), `Use-Operator-Units: true`
  при желании списывать баллы оператора.
- Тело запроса: `{ "method": "...", "params": { ... } }`. У большинства сервисов
  методы: `add`, `update`, `delete`, `get`, `suspend`, `resume`, `archive`,
  `unarchive`, `moderate`.
- Выборка (`get`): `SelectionCriteria`, `FieldNames`, вложенные `*FieldNames`,
  пагинация через `Page: { Limit, Offset }`; в ответе `LimitedBy` — курсор для
  следующей страницы. Реализуй авто-пагинацию (итератор, который дочитывает всё).
- **Баллы (units)**: после каждого ответа в заголовке `Units` приходит
  `потрачено/остаток/суточный лимит`. Парси и отдавай наружу — это критично,
  чтобы синхронизация не упёрлась в лимит.
- **Частичный успех**: в ответах `add/update/delete` каждый элемент имеет свой
  результат — часть может быть `Errors`, часть `Warnings`, часть успех. Никогда
  не считай весь запрос успешным по HTTP 200 — разбирай поэлементно.
- Ошибки: код + сообщение + детали (`error_code`, `error_string`, `error_detail`).
  Отдельно обрабатывай `152` (недостаточно баллов) и `56` (превышен лимит запросов
  → бэкофф).

## Что сделать

1. **Транспорт** (`client.ts`): fetch-обёртка с заголовками, retry с
   экспоненциальным бэкоффом на сетевые/`5xx`/`error_code 56`, таймауты,
   учёт `Units` (эмить событие/колбэк с остатком баллов).
2. **Типы**: сгенерируй TypeScript-типы запросов/ответов для сервиса `$1`
   (SelectionCriteria, поля, enum статусов). Держи их в `src/direct-api/types/`.
3. **Сервисные обёртки**: по одному модулю на сервис с методами-хелперами
   (`getAll`, `add`, `update`, `delete`, статусные операции), возвращающими
   разобранный поэлементный результат.
4. **Разбор частичного успеха**: единый тип `BulkResult<T>` c массивами
   `succeeded / failed / warnings` и удобным доступом к причинам.
5. Тесты (Vitest) на транспорт: заголовки, пагинация, парсинг `Units`, разбор
   ошибок и частичного успеха — с замоканным fetch.

## Критерии готовности

- Клиент работает против **sandbox** без правки боевых данных.
- Пагинация дочитывает все страницы сама.
- `Units` доступны вызывающему коду после каждого запроса.
- Тесты на разбор частичного успеха и ретраи проходят.
